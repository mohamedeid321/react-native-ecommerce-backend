# Performance benchmark

Run GitHub Actions "Backend performance benchmark" on develop/lotta-web-backend. It uses disposable runner-local MongoDB replica set and Redis, full Express application, and 300 synthetic products plus 1000 synthetic customers. No production data or external notifications. Test credentials and session tokens are generated locally and removed; do not upload fixtures.

1. Ten simultaneous password logins (below the per-IP rate limit; not a sustained login throughput test).
2. Sixty unique customers compete for 30 units, each submitting two requests with the same idempotency key. Database assertions require exactly 30 orders, 30 unique customers and numbers, zero remaining stock, and rejected carts preserved. HTTP 409 for insufficient stock is expected, not a server failure.
3. Mixed public catalog, search, categories, settings and authenticated cart reads at 10, 50, 100, 250, 500 and 1000 distinct virtual users for 15 seconds each, with a 0.5s think time. Stop escalation when a threshold fails. Record throughput, p95 latency and errors. Read target p95 <500ms overall and per endpoint, error rate <1%; checkout and login p95 <2s. These are initial smoke gates, not production SLAs.

The runner shares resources between k6, MongoDB, Redis and the API; its results cannot be used as Vercel/Atlas/Upstash capacity figures. The checkout counter and hot product row intentionally stress transaction conflicts. A failed gate requires diagnosis and retest, not raising the threshold.

For authorized staging: use separate test project/data, same-site HTTPS and provider plans, monitor p95, p99, CPU, memory, MongoDB connections/queries, Redis requests and serverless cold starts. Repeat successful CI levels on staging gradually, and run a one-hour soak only after lower levels pass and quotas permit. Initial business target <0.1% unexpected errors requires longer runs and larger samples. Avoid load tests against production; never disable rate limits to simulate login. k6 VUs are active simulated sessions, not request-per-second counts.

Optimize from measured evidence: inspect query execution plans and index use, avoid repeated expensive counts or unbounded reads, evaluate cache of non-sensitive catalog metadata with expiry/invalidation, preserve fresh stock/prices at checkout, tune connection pool per deployment, and keep post-commit tasks reliable. Do not cache private customer/admin responses publicly.

Runner variability means the first successful 500-VU result is not a stable capacity guarantee.

The subsequent cart GET uses one indexed aggregation to join the caller's cart to current active products, previous-order eligibility and pricing settings, without caching prices, stock or personal data. Mutations keep optimistic concurrency, checkout still validates authoritative data in the transaction. Hidden items are filtered on reads and may be removed on subsequent cart mutations. Retest against the identical workload before changing thresholds. For a longer soak, start with 5–10 minutes below the measured capacity; pre-seeded access cookies expire after 15 minutes, so a one-hour authenticated test requires a realistic refresh plan and should not bypass production rate limits.

## Redis public cache (opt-in)
PUBLIC_CACHE_ENABLED=1 enables bounded shared Redis caching for public product lists and searches (5 seconds), and category lists (30 seconds); PUBLIC_CACHE_NAMESPACE separates environments. Product/category admin writes invalidate affected namespaces by generation; generation-checked writes prevent an old in-flight result from being reinserted after invalidation. A request already in flight can still see the earlier snapshot. Public stock display can lag checkout by up to the short TTL. Cart/checkout/settings enforcement, product detail, admin data, auth and finance remain authoritative and uncached. No cache of private responses. Cache failure falls back to MongoDB, with a 150 ms command budget and 1 s circuit cooldown. Each namespace has 64 bounded slots; collisions miss safely, entries above 64 KiB are not retained. Session keys are not cleared or evicted by cache code. Use a separate staging Redis namespace/instance and monitor commands, latency, memory and provider limits; never enable eviction of session data. Keep the flag off until staging checks pass.

CI performance workflow enables cache for gradual reads and a five-minute 250 VU soak, then restarts the same runner API with caching disabled for a diagnostic 1000 VU comparison. Baseline is a short closed-model synthetic workload; repeated queries are deliberately cacheable, so benchmark does not establish real-world hit rate. Compare actual workload diversity and Upstash network latency/cost on staging before concluding a production benefit. No production change or deployment is authorized by this benchmark.

## Mixed shopping workload
Separate workflow starts fresh runner-local Mongo/Redis, 1000 distinct synthetic accounts, 20 well-stocked products, empty carts and no existing orders. For 60 seconds, 850 accounts browse, 100 repeatedly merge/change/delete cart lines, 50 stagger one purchase of two units and repeat checkout with the same key, then browse. Gates: 50 successful purchase journeys, at least 100 successful cart writes, <0.1% unexpected errors, read p95 <500 ms, cart-write p95 <1000 ms, checkout p95 <2000 ms. Database verification requires 50 unique orders, 100 units sold and reconciled stock, and 50 emptied buyer carts. The test uses pre-seeded sessions; password login is covered separately. Not an actual browser or production deployment benchmark.

## Real refresh endpoint benchmark
Dedicated isolated runner starts the unmodified full Express API. 1000 distinct synthetic sessions are spread across 20 real runner-local loopback source IPs (50 sessions/IP), staying below the production rate limit of 60 refresh requests per IP per 15 minutes. It verifies every refresh rotates cookies and the new access cookie retrieves the matching user. Reusing the first refresh cookie must revoke its session, and the 61st refresh from that IP must be rejected with 429. It measures p95 of the refresh burst against a 2-second target. No forged proxy headers, modified production limits, or production data. Real proxy/NAT behavior still needs staging checks. This test simulates a burst, not the rate of session refreshes during a typical hour.

Test-only session access tokens were renewed between segments, not through the real API; checkout was tested in the initial mixed minute. Run 45659356752 independently verified 1000 real refresh operations, 841 refreshes/s, p95 1114 ms, zero unexpected errors, old-token reuse rejection and IP rate limit preserved. Local readiness startup logged an initial Mongo connection refusal before healthy startup. No production infrastructure capacity claim.

## Authorized staging public load
Install k6 locally and configure a dedicated HTTPS hostname containing a `staging` label. Set STAGING_BASE_URL and STAGING_APPROVED_ORIGIN to the same exact origin, CONFIRM_STAGING=yes, and STAGING_MAX_VUS=10 initially. Run `node scripts/staging-load.js`. Raise the maximum through 50, 100, 250, 500 and 1000 only after reviewing provider quotas/costs and prior levels. Each stage lasts 30 seconds with user think time, no redirects, readiness check, error threshold <0.1%, p95 <500 ms; escalation stops on failure. This is read-only and not a substitute for authenticated staging cart/order or browser acceptance. Never target production. No staging run has been performed yet.
